    一、项目背景¶

    1.1 所属行业分类¶

    殡葬服务行业（殡仪服务、墓园运营、殡葬用品、悲伤辅导、文化礼仪）

    1.2 为什么做这个项目¶

    某国内领先殡葬服务集团是涵盖殡仪服务、墓园运营、殡葬用品、生命文化研究于一体的综合性殡葬服务企业，业务覆盖全国15个省份，运营殡仪馆和墓园30+处，员工3000+人，年服务家庭10万+。集团核心资产是多年积累的殡葬服务知识体系——与殡仪流程、墓葬服务、法规政策、心理疏导、文化习俗相关的文档规模超8万篇，包括殡仪服务流程手册、仪式方案说明、礼仪规范指南、殡葬用品使用说明、墓型介绍资料、风水知识文献、安葬流程规范、祭扫服务指南、殡葬管理条例、地方政策文件、收费标准说明、惠民政策汇编、悲伤辅导资料、心理自助手册、家属沟通话术、危机干预方案、各地丧葬习俗记录、宗教信仰礼仪说明、民族传统文献、现代殡葬文化研究等，分散在业务管理系统、CRM客服系统、培训平台、法规数据库、心理咨询资源库、文化研究中心等7+业务系统中。

    殡葬服务从业人员的日常工作高度依赖对这些分散文档的检索与理解。一位殡仪服务师在接待家属时，平均需要查阅8-12份文档（殡仪流程手册、仪式方案库、礼仪规范、用品说明、地方政策等），单次检索耗时超20分钟；墓园顾问在面对家属关于墓型选择、安葬流程、风水讲究等咨询时，常需翻阅多个系统确认信息；心理咨询师在处理丧亲家属的悲伤情绪时，需要快速查找悲伤辅导资料、危机干预方案、沟通话术参考；客服每天处理400+条咨询，遇到复杂问题（如"跨省运骨灰需要什么手续""少数民族丧葬有什么特殊政策""海葬流程怎么申请"）常需多部门协调确认。

    此前，集团曾搭建过一套基于关键词检索的内部知识库，但实际使用率极低——殡仪服务师和家属提问高度口语化且带有情感色彩（如"亲人走了以后第一步该做什么""老人家信佛，后事怎么办""经济困难有没有丧葬补贴"），关键词检索系统无法理解自然语言表述，且缺乏对悲伤情绪的敏感度，检索准确率不足18%，上线半年后日活降至不足4%。

    2024年5月，该集团启动"殡葬服务智能咨询助手"项目公开招标，要求系统具备自然语言问答、多源知识整合、策略化检索、流式输出、情感关怀等能力。我们公司凭借在RAG（检索增强生成）领域的技术积累和社会服务行业知识库建设经验成功中标。我作为核心开发成员，负责RAG检索引擎设计、5大向量知识库搭建、三级缓存架构实现及殡葬领域LLM微调等核心模块的开发。

    1.3 项目的痛点¶

    • 殡仪服务知识查询效率低：殡仪流程、仪式方案、礼仪规范、用品说明等散落在7+系统中，服务师遇到复杂案例平均需要20分钟+才能确认答案
    • 法规政策信息分散：殡葬管理条例、地方政策、收费标准、惠民政策等文件数量庞大且更新频繁，服务师和家属无法快速获取最新政策信息
    • 心理疏导资源查找不便：悲伤辅导资料、心理自助手册、家属沟通话术、危机干预方案等专业知识分散在不同资源库中，心理咨询师和一线服务师缺乏统一查询入口
    • 文化习俗差异大：集团业务覆盖15个省份，各地丧葬习俗、宗教信仰礼仪、民族传统差异大，服务师跨区域服务时需要大量时间查阅当地习俗资料
    • 家属咨询响应慢：逝者家属在悲痛中咨询殡仪流程、政策手续、费用标准等问题，人工响应平均需要30分钟，严重影响服务体验和家属满意度
    • 新人培训周期长：殡葬服务涉及专业知识广泛，新入职服务师平均需要3个月才能独立上岗，培训成本高

    1.4 项目的价值¶

    • 殡仪咨询响应提速600倍：单次殡仪咨询响应时间从30分钟缩短至3秒
    • 服务师方案查询效率提升8倍：单次服务方案查询时间从20分钟缩短至2.5分钟
    • 家属满意度提升25%：7×24小时秒级响应，专业温和的解答显著提升家属在服务期间的体验
    • 新人培训周期缩短50%：新服务师入职熟悉期从3个月缩短至6周
    • 知识资产统一管理：RAG架构动态接入7+业务系统，文档更新自动同步，确保引用最新政策法规和服务规范

    1.5 目标用户¶

    • 逝者家属：亲人离世后需要了解殡仪流程、仪式方案、政策法规、费用标准、心理调适方法
    • 殡仪服务师：负责殡仪服务接待和流程执行，需要快速查询殡仪流程、仪式方案、礼仪规范、用品说明
    • 墓园顾问：负责墓园咨询和安葬服务，需要快速查询墓型介绍、风水知识、安葬流程、祭扫规范
    • 心理咨询师：负责丧亲家属的心理疏导，需要快速查找悲伤辅导资料、沟通话术、危机干预方案
    • 客户经理：负责客户关系维护和业务拓展，需要查询政策法规、收费标准、惠民政策

    二、项目核心要点¶

    本节帮助你快速了解项目的重点，知道面试应该侧重准备哪些内容。

    2.1 项目核心价值¶

    殡葬服务行业RAG系统的核心价值：该行业知识库具有政策法规性强、文化习俗多样性、情感关怀要求高、跨区域差异大等特点。RAG系统能将分散在各业务系统中的殡仪知识、墓葬信息、法规政策、心理疏导资源、文化习俗资料整合为统一的智能问答平台，在尊重逝者、关怀家属的前提下，大幅提升服务效率和服务质量。

    2.2 效果关键环节¶

    1. 文档解析质量：直接决定了知识库的数据质量。如果解析丢失殡仪流程细节、政策法规条文、丧葬习俗描述或心理疏导话术，后续检索和回答都会出错，甚至可能给悲痛中的家属带来不当信息。
    2. 分块策略：分块粒度影响检索的召回率和精度。按服务类型分块（殡仪服务、墓葬服务、法规政策、心理疏导、文化习俗）可以让同一服务领域的相关知识集中在一个chunk中，检索更精准。
    3. 检索策略：不同难度的问题需要不同的检索方式。简单政策查询直接检索，复杂的跨领域问题（如涉及法规+习俗+心理的综合咨询）需要改写或分解查询。
    4. 重排序（Rerank）：对初步检索结果做二次排序，显著提升Top-K精度，是提升最终回答质量的关键环节。

    1. 分块策略选择
    2. 面试官可能问："分块策略选择是怎么做的？"

    • 分块策略：殡葬文档采用按服务类型分块策略——将殡仪服务、墓葬服务、法规政策、心理疏导、文化习俗五大领域分别组织为独立chunk集合，每个领域内按子主题进一步细分（如殡仪服务按"接运→冷藏→整容→告别→火化→安葬"环节分块），保留服务类型、适用地区、民族/宗教标签作为metadata；法规政策按条款自然分段，不截断完整条款，保留法规编号和生效日期；文化习俗按地区和民族分块，保留地域标签和宗教/民族属性
    • 向量化处理：使用BGE-M3 Embedding模型（1024维），针对殡葬服务文本specialized处理，支持殡葬术语（"告别仪式""落葬""合葬""骨灰安放""生态葬"）、政策法规术语（"惠民殡葬""基本殡葬服务""丧葬补助金"）、心理学术语（"悲伤五阶段""复杂性悲伤""创伤性哀伤"）、文化习俗术语（"做七""头七""回煞""风水""朝向"）的精确语义表示
    • FAQ处理：三级缓存设计 — Redis存储Top 2000高频问题（TTL=24h）→ MySQL存储全量FAQ索引 → BM25倒排索引支持全文模糊匹配（阈值0.85）
    • 数据更新：增量更新机制——法规政策库监听民政部及各省民政厅公告自动更新；收费标准每年集中更新一次；文化习俗库根据田野调研持续补充；心理疏导库每季度更新自助资料；殡仪流程和墓型信息在业务变更时即时同步
    • 多角色内容隔离方案：系统采用"RBAC 角色权限 + metadata 过滤"的隔离策略：
      1. 角色隔离：逝者家属、殡仪服务师、墓园顾问、心理咨询师、客户经理 不同角色可见内容范围不同
      2. metadata 过滤：通过 user_role、access_level 字段控制检索范围
      3. Redis 缓存隔离：缓存 key 按角色前缀隔离
      4. FAQ 权限：FAQ 标记 visible_to_roles 字段，三级缓存匹配后还需校验用户角色

    4.4 面试常见问题¶

    Q1：你们的殡葬服务智能咨询助手和直接用大模型对话有什么区别？

    直接用大模型存在三个核心问题：一是知识截止，模型不了解最新的殡葬管理政策（如最新的惠民殡葬减免政策、生态葬奖补标准、各省市调整后的殡葬服务收费标准）；二是幻觉风险，可能编造不存在的政策条款或错误的丧葬习俗，在殡葬这个高度敏感的领域，错误信息可能对处于悲痛中的家属造成严重伤害；三是缺乏企业私有知识和人文关怀，无法回答该集团特有的服务流程、仪式方案、价格体系，也无法以温和、专业、尊重的方式与悲伤中的家属沟通。我们的RAG系统通过实时检索8万+篇私有知识库确保回答有据可查，通过三级缓存+4种检索策略确保准确率94%以上，通过引用来源标注（法规编号、政策文件名称、习俗地区）让服务师和家属可一键验证，同时在Prompt模板中内置温和、尊重、共情的回答风格指引。

    Q2：为什么要设计4种检索策略（Direct/HyDE/SubQuery/Backtrack），不能只用一种吗？

    殡葬服务场景的问题复杂度差异极大。简单事实查询（如"遗体接运需要什么手续"）法规政策库有明确答案，用Direct即可。研究型问题（如"老人去世后家属应该怎么调节情绪"）描述较宏观，HyDE策略先让LLM生成假设性分析"需要考虑悲伤情绪的正常化、社会支持系统的建立、专业帮助的时机判断"，再向量化去心理疏导库检索。多维问题（如"外省去世的老人想在老家安葬，需要什么手续和流程"）涉及多个知识领域，SubQuery拆解为"跨省遗体运输规定"+"老家丧葬习俗"+"安葬流程手续"三个子问题并行检索。多轮追问场景（第一轮"父亲去世了，佛教仪式的告别怎么做"，第二轮"那花圈挽联怎么写"），Backtrack回溯关联上下文检索。单一策略无法同时覆盖，实测4策略路由后准确率比纯Direct提升14个百分点。

    Q2a：能举几个具体例子说明四种策略各自适合什么殡葬服务场景吗？

    Direct策略：家属问"办理死亡证明需要哪些材料？"——意图单一、法规政策库有明确答案，直接检索命中，返回"办理死亡证明需携带：①申请人身份证；②医疗机构出具的死亡医学证明或公安机关出具的死亡证明；③逝者户口簿或身份证…"。HyDE策略：家属问"失去亲人后一直睡不着觉怎么办？"——模糊研究型，先让LLM生成假设分析"需要考虑这是丧亲后正常的悲伤反应，可能涉及睡眠障碍的自助调适方法，需要判断是否需要专业心理咨询介入"，再向量化去心理疏导库检索相关自助手册和专业建议。SubQuery策略：家属问"我父亲是回族人，去世后丧葬有什么讲究？"——拆解为①回族丧葬礼仪和宗教仪轨（伊斯兰教丧葬规定、速葬土葬要求、净身穿白布等） ②当地回族公墓或安葬地点 ③相关政策法规（少数民族丧葬政策），并行检索文化习俗库、墓葬知识库和法规政策库合并去重。Backtrack策略：服务师先问"传统告别仪式的流程是什么"，再追问"那挽联怎么写"——回溯上一轮告别仪式主题上下文，结合"告别仪式+挽联"组合检索更精准的礼仪规范文档。

    Q3：三级缓存的设计思路是什么？为什么不直接全走Milvus向量检索？

    殡葬服务问答有明显的"二八效应"——20%的高频问题占据了60%以上查询量。家属和服务师频繁问类似问题（如"火化需要准备什么材料""基本殡葬服务费用能减免吗""清明祭扫有什么规定"），每次都走向量检索+LLM既浪费算力又增加延迟，对于正在悲痛中等待的家属来说响应速度尤为重要。三级缓存设计理念是"能用缓存就不用检索"：Redis缓存最热FAQ（命中率16%，响应<50ms）；MySQL FAQ库存放6万+标准问答对，BM25匹配（阈值0.85，命中率14%）；BM25全文索引兜底（命中率7%）。三级合计命中率37%，只有63%的长尾问题走完整RAG Pipeline，LLM调用成本降低约42%。

    Q4：BGE-M3相比其他Embedding模型有什么优势？为什么选它？

    选择BGE-M3主要基于三个原因：一是中文殡葬专业术语理解能力强——殡葬场景包含大量行业术语（"告别仪式""落葬""合葬""骨灰安放""生态葬""海葬"）、政策法规术语（"惠民殡葬""基本殡葬服务费""丧葬补助金""抚恤金"）、心理学术语（"悲伤五阶段""复杂性悲伤""创伤性哀伤"）、文化习俗术语（"做七""头七""回煞""风水""朝向""寿衣""棺木"），语义表示显著优于通用模型；二是支持Dense、Sparse、ColBERT三种检索粒度，混合检索效果优于单一粒度；三是1024维输出在精度和性能间平衡良好，Milvus单条查询延迟<100ms。对比测试中BGE-M3在我们的数据集上Recall@10达91.5%，优于text-embedding-ada-002（86.2%）和BGE-large-zh（88.8%）。

    Q5：如何保证系统的回答质量？怎么评估RAG系统的效果？

    我们使用RAGAS评估框架，核心关注四个指标：Faithfulness（忠实度，防止编造政策条款和丧葬习俗，目标>0.85）、Answer Relevancy（答案相关性）、Context Precision（上下文精确度，目标>0.85）、Context Recall（上下文召回率）。此外构建了500条人工标注测试集（Golden Dataset），覆盖6类意图，由资深殡仪服务师、墓园顾问、心理咨询师和业务顾问联合标注，每月回归测试。上线后建立用户反馈机制，差评回答自动进入人工审核队列，特别是涉及政策法规和民族禁忌的回答实施100%人工抽检。RAGAS评估Faithfulness达0.88，整体问答准确率94.0%。

    Q6：系统如何处理多角色的内容隔离？

    角色隔离 + metadata 过滤：逝者家属、殡仪服务师、墓园顾问、心理咨询师、客户经理不同角色可见内容范围不同。比如家属只能看到公开的殡仪流程和常见问答，殡仪服务师可访问完整服务流程手册和仪式方案库，心理咨询师可访问悲伤辅导资料和危机干预方案，客户经理可访问收费标准和惠民政策。通过 user_role、access_level metadata 字段控制检索范围，Redis 缓存 key 按角色前缀隔离，FAQ 有 visible_to_roles 权限字段。隔离查询额外延迟 < 5ms。

    推理框架：vLLM¶

    我们用的 vLLM 是专门为大模型生产环境设计的推理引擎：

    • PagedAttention：把 KV Cache（模型生成时缓存的中间结果）分页管理，显存利用率提升 2-4 倍——同样一张卡能同时服务更多用户
    • Continuous Batching：传统方案像坐大巴（等人齐了才发车），Continuous Batching 像坐地铁（随时进人），吞吐量提升 3-5 倍
    • Tensor Parallel：大模型一张卡装不下时，"切"到多张卡并行计算

    离线数据处理阶段：

    离线阶段的核心任务是将集团7+业务系统中的8万+篇文档转化为可检索的向量知识库。首先，数据接入层通过API、文件导出、Webhook等方式从业务管理系统、CRM客服系统、培训平台、法规数据库、心理咨询资源库、文化研究中心等系统中获取原始文档。文档格式包括PDF、Word、Excel、HTML等多种类型，使用MinerU进行高质量文档解析，保留文档结构、表格、列表等格式信息。

    解析后的文档进入清洗和分块环节。殡葬文档采用按服务类型分块策略——将殡仪服务、墓葬服务、法规政策、心理疏导、文化习俗五大领域分别组织为独立chunk集合，每个领域内按子主题进一步细分。例如殡仪服务库按"接运→冷藏→整容→告别→火化→安葬"环节分块，文化习俗库按地区和民族分块。每个chunk保留服务类型、适用地区、民族/宗教标签、法规编号等metadata信息。分块后的文本使用BGE-M3模型（1024维）进行向量化，然后分别存入Milvus向量数据库的5个Collection中。

    同时，6万+条FAQ经过处理后构建三级缓存体系：Redis存储Top 2000高频问题（TTL=24小时）用于最快响应；MySQL存储全量FAQ索引支持BM25精确匹配（阈值0.85）；BM25全文索引覆盖所有文档支持模糊检索。

    在线查询应答阶段：

    以一个真实的查询场景为例进行walkthrough——逝者家属提问："我父亲是回族人，在新疆去世，想在老家甘肃安葬，需要什么手续？当地有什么丧葬习俗？"

    ① 用户输入问题 → ② 前置问候语检测（非问候语，进入正式处理流程）→ ③ Fine-tuned Qwen2.5-7B进行意图识别，判断为多意图混合查询（涉及"法规政策"+"文化习俗"+"墓葬咨询"），主意图判定为"法规政策"，准确率91.0% → ④ 三级缓存查询：Redis未命中（该问题为个性化长尾问题）→ MySQL BM25未命中（阈值0.85，相似度不足）→ BM25全文索引未命中 → ⑤ 策略选择器分析问题包含多个维度（跨省手续+民族习俗+安葬流程），判定为SubQuery策略 → ⑥ SubQuery拆解为三个子查询：子查询A"跨省遗体运输手续规定"检索法规政策库、子查询B"回族丧葬习俗和仪轨"检索文化习俗库、子查询C"甘肃地区安葬流程"检索墓葬知识库 → ⑦ 三个子查询并行执行BGE-M3向量化 → 分别对Milvus法规政策库、文化习俗库、墓葬知识库进行Top-K=10检索 → Reranker重排序取Top-5 → ⑧ 合并去重后得到最相关的12篇文档（含《殡葬管理条例》跨省运输规定、回族丧葬礼仪规范、甘肃地区丧葬习俗资料、少数民族丧葬政策等）→ ⑨ Prompt组装：12篇检索文档（含法规编号和习俗地区标签）+ 原始问题 + 最近5轮对话历史 + 温和尊重风格的系统提示 → ⑩ Qwen2.5-14B生成结构化回答：先表达哀悼和关怀，再分三部分回答（跨省运输手续、回族丧葬习俗要点、甘肃安葬流程），最后温馨提示可联系当地殡仪馆获取具体协助 → ⑪ WebSocket流式推送至前端，文字逐字显示，让焦急等待的家属能实时看到回答进度 → ⑫ 异步存入MySQL conversations表和Redis缓存，标注服务类型、地区标签、满意度评分，供后续分析和知识库优化使用

    这个案例展示了系统的核心能力：面对跨领域的复杂查询，通过SubQuery策略将问题分解为多个子查询并行检索不同知识库，最终整合生成完整、准确、有温度的回答。整个流程从用户输入到首Token输出控制在800ms以内，完整回答在5-10秒内完成。

    5.2 核心查询流程¶

    1. 用户输入问题：如"亲人去世后第一步应该做什么？殡仪流程是怎样的？"
    2. 前置检测：问候语/闲聊检测，是则返回温暖问候语（如"您好，首先对您的失去表示深切哀悼。请问有什么可以帮到您的？"）
    3. 意图识别：Fine-tuned Qwen2.5-7B判断为"殡仪咨询"
    4. 三级缓存查询：Redis → MySQL（BM25阈值0.85）→ BM25全文索引 → 若命中直接返回缓存答案
    5. 策略选择：问题为简单流程查询，策略选择器判定Direct
    6. Direct检索：BGE-M3向量化 → Milvus殡仪服务库Top-K检索 → Reranker重排序 → 返回最相关5篇殡仪流程文档
    7. 向量检索：Milvus Top-K → Reranker重排序 → 返回完整的殡仪服务流程说明（接运→冷藏→整容→告别→火化→安葬各环节要点）
    8. Prompt组装：检索到的殡仪流程文档 + 原始问题 + 最近5轮对话历史 + 温和尊重风格提示
    9. LLM生成：Qwen2.5-14B生成结构化回答，以温和关怀的语气开头，分步骤说明殡仪流程各环节要点和注意事项
    10. 流式输出：WebSocket流式推送，异步存入MySQL conversations表和Redis缓存

    7.2 想增加知识图谱等高级功能？¶

    如果你想在项目中加入更前沿的技术（比如知识图谱、多模态RAG、Agent），可以这样操作：

    步骤1：了解基本概念 先问 AI 工具："用通俗的语言解释什么是知识图谱，它在 RAG 系统中起什么作用？"

    步骤2：设计集成方案 告诉 AI："我想在现有的 RAG 项目中加入知识图谱，帮我设计一个集成方案，包括：数据从哪里来、怎么构建图谱、怎么和向量检索结合。"

    步骤3：写入文档 让 AI 帮你把方案写入文档的「附带信息」部分，作为加分项。

    示例扩展方向： - 知识图谱 + RAG：对行业实体关系建模（如殡葬法规引用关系、各地习俗关联关系、医疗中的疾病-症状-药物关系），增强多跳推理 - 多模态 RAG：支持图片、表格的理解和检索（适合殡仪场景布置图、墓园规划图、丧葬用品图等多模态内容） - Agent 化升级：让大模型自主决策检索策略，而不是固定流程

    7.3 遇到不懂的概念怎么办？¶

    方法1：直接问 AI

    "文档里提到了 MinerU，我不太了解。它是什么？和 PyPDF 有什么区别？面试时怎么介绍？"

    方法2：让 AI 帮你写学习笔记

    "帮我把文档中涉及的所有技术概念整理成一个术语表，每个概念用一句话解释，并给出面试时的回答模板。"

    方法3：让 AI 模拟面试

    "请你扮演面试官，根据这份项目文档问我 5 个面试问题。等我回答后，给出评价和改进建议。"

    7.4 快速改造检查清单¶

    改造完成后，逐项检查：

    • [ ] 行业背景是否真实可信？（公司名、规模、痛点要具体）
    • [ ] 数据规模是否合理？（参考同类产品的公开数据）
    • [ ] 技术栈是否匹配？（不同行业有不同偏好）
    • [ ] 用户规模是否和部署方案对齐？（DAU 100 和 DAU 10000 的部署方案完全不同）
    • [ ] Q&A 是否覆盖了该行业的面试重点？
    • [ ] 成果数据是否有对比基线？（优化前 → 优化后）
    • [ ] 项目时间线是否与相关模型发布时间匹配？

    💡 核心原则：改造后的项目要能让你在面试中自信地说出每一个细节。如果某个部分你说不清楚，就让 AI 帮你简化，直到你能完全理解为止。宁可简单但真实，不要复杂但露馅。
